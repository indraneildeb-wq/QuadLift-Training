OceanBridge MCP Server

A Model Context Protocol server that gives AI agents controlled access to OceanBridge's shipments, freight tariffs, reroute options, carrier negotiation and purchase orders. It is how the CrewAI agents in this project read live shipment data and commit reroutes, and any MCP client can use it the same way.

Built withFastMCP · MCP SDK 1.28
Protocol2025-11-25
Transportsstdio · SSE · Streamable HTTP
Tools5
Sourcepackages/mcp-servers/src/oceanbridge/mcp_servers/supply_chain_core/

Three tools come straight from the capstone requirement: get_shipment_status, calculate_freight_cost and issue_purchase_order. Two more, list_route_alternatives and submit_sla_proposal, give the Route Optimizer and Vendor Negotiation agents what they need to do their jobs.

Architecture

The server is a thin layer. Each tool validates its arguments, calls one function in oceanbridge.core.service, and wraps the result in a JSON envelope. All business rules live in the core, so the REST API, the offline agents and MCP clients all get the same behaviour.

Connect a client

From CrewAI (how this project does it)

All MCP servers live in the oceanbridge.mcp_servers package, which keeps a registry of them. The CrewAI agents never hard-code a server: agents/common/mcp_tools.py asks for tools by name, and the registry says which server provides them. That server is started over stdio on first use.

Python · agents/common/mcp_tools.py (simplified)
from crewai_tools import MCPServerAdapter
from oceanbridge.mcp_servers import SERVERS, stdio_params

spec = SERVERS["supply_chain_core"]              # module + the 5 tool names
params = stdio_params("supply_chain_core", env={"OB_DB_PATH": "data/oceanbridge.db"})
adapter = MCPServerAdapter(params, *spec.tools)
tools = {t.name: t for t in adapter.tools}       # hand these to an Agent(tools=[...])
...
adapter.stop()

Each agent declares the tools it needs in its own folder. For example, agents/vendor_negotiator/agent.py uses submit_sla_proposal, issue_purchase_order and get_shipment_status.

From the Python MCP SDK

Python · same pattern as packages/mcp-servers/tests/test_mcp_server.py
import asyncio, json, sys
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command=sys.executable, args=["-m", "oceanbridge.mcp_servers.supply_chain_core"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            print([t.name for t in (await session.list_tools()).tools])
            res = await session.call_tool("get_shipment_status", {"shipment_id": "SHP-1004"})
            print(json.loads(res.content[0].text)["risk"])

asyncio.run(main())

list_route_alternatives

◆ Writes proposals

Prices every sensible reroute for a shipment under the active disruptions and ranks them by landed-cost score: freight, plus inventory holding, plus lateness penalties, plus risk exposure. Candidates include a different sea path (Cape instead of Suez), a nearby port plus trucking, China–Europe rail, air, sea-air through Dubai and the US land bridge. STAY means keeping the current booking. Options that would land later than absorbing the delay are left out.

Side effect

The returned options are saved as the shipment's current proposal. submit_sla_proposal and issue_purchase_order refer to options by option_id from this list, so call this tool first. Calling it again replaces the proposal.

submit_sla_proposal

◆ Writes negotiation log

Sends a price and SLA offer to the carrier that runs the option's main leg. The carrier is simulated. It either accepts or returns a counter-offer and the SLA terms it can live with. Each round it concedes more, down to a price floor set by its margin and flexibility. The terms it accepts depend on its on-time reliability.

Responses & errors

Tools never raise to the client. Every call returns one of two shapes, so an agent can read a failure and change course.

success
{ "ok": true, …tool-specific fields… }
failure
{ "ok": false, "error": "<ExceptionType>", "message": "…" }
errorMeaningWhat the caller should do
PolicyViolationA business rule refused the action: HITL sign-off needed, approval not valid, amount above quote, STAY chosen, or the round limit reached.Do not retry the same call. Route the reroute through the Approval Queue, or pick another option.
KeyErrorUnknown shipment, option or approval, or no proposal saved yet.Check the id, and call list_route_alternatives first.
ValueErrorInvalid lane or mode (e.g. road across the sea), unknown port, carrier not running that mode, or not enough capacity.Fix the arguments or choose another carrier or option.
ValidationErrorArguments or sla_json do not match the expected fields or types.Send every required SLA field with a numeric value.

HITL enforcement inside the tool

The pipeline already applies the HITL gate before it calls the negotiation agent. issue_purchase_order applies it again, so a misbehaving agent or any other MCP client cannot bypass human approval. The checks live in the HITL package, in hitl/guard.py (authorize_purchase_order), and use the same policy as the pipeline (hitl/gate.py). They run in this order:

  1. If an approval_id is given, it must exist and must not be EXECUTED already.
  2. The option is taken from the approval if one is given, otherwise from the saved proposal, and its id must match option_id. STAY is refused because keeping the booking needs no PO.
  3. amount_usd may not exceed the option's quoted total cost.
  4. The gate is evaluated: cost increase against the currently booked cost, and the cargo value. Auto-execute only if the increase is under 5% and the value is under $250,000.
  5. If either limit is reached and there is no approval, the call is refused and po_refused is written to the audit log. An approval that belongs to another shipment, or is not APPROVED, is also refused.
  6. Capacity is reserved, the PO is issued, the old PO is marked superseded, and the shipment is rerouted. The approval becomes EXECUTED, so it can only be used once, and po_issued is written to the audit log.
Getting an approval id

Approvals are created by the pipeline's HITL gate and decided by a Logistics Operations Manager in the Control Tower UI or through POST /approvals/{id}/approve on the REST API. There is no MCP tool that approves, on purpose: an agent must never be able to approve its own request.

Typical call sequence

This is how the Vendor Negotiation agent uses the server for one reroute.

  1. get_shipment_status: confirm the shipment is at risk and has no pending approval.
  2. list_route_alternatives: get priced options and save them as the proposal.
  3. calculate_freight_cost (optional): check a specific leg or forced route, e.g. Cape instead of Suez.
  4. submit_sla_proposal: open about 8% below list, move toward each counter, and accept the carrier's counter by round 3.
  5. issue_purchase_order: commit once with the agreed amount and SLA, passing approval_id when a sign-off was needed.

Limitations

  • The SSE and Streamable HTTP transports have no authentication. They bind to 127.0.0.1 by default; do not expose them on a network without adding auth in front.
  • Tool calls are tested over stdio. The SSE transport has been started and accepts connections, but tool calls over SSE and Streamable HTTP have not been run end to end.
  • The server reports the MCP SDK version (1.28.1) as its own version.
  • Cache tiers L1 and L2 live in the server process, so the MCP server and the REST API each keep their own. L3 is shared through SQLite.
  • Shipments, feeds, carriers and tariffs are simulated.
